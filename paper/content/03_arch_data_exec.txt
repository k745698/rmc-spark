@section Multi-Cluster Spark Analytics Architecture

@sub Design Principles

Four principles guided the design. First, leave the engine alone: every cluster runs stock Apache Spark in standalone mode, so the approach fits existing deployments. Second, decouple jobs from clusters: a job has a stable identifier, its durable state sits in shared object storage, and the cluster running an attempt is a replaceable resource. Third, act on evidence of harm, not suspicion: an unwell cluster gets no new work, but a running job moves only once it has stopped progressing. Fourth, explain every action, because operators will not trust recovery they cannot check [@li2020predicting, @notaro2021survey].

@sub Overall Architecture

Fig. {fig:architecture} shows the deployed architecture. Two Spark clusters, A and B, each have one master and two workers. A shared MinIO object store, reached through the Hadoop S3A connector, holds inputs, stage and streaming checkpoints, and results. Prometheus collects metrics and Grafana displays them. The controller has its own container and hosts the Spark drivers, launching every job with spark-submit in client mode, so each driver lives outside the cluster whose executors it uses. A fault injector controls each cluster's containers through the Docker Engine API.

@figure architecture | Fig 06 Resilient Multi-Cluster Spark Architecture | Resilient multi-cluster Spark architecture (core figure): drivers run in the controller, executors on cluster A or B, and durable state in shared storage, so a job can resume on either cluster. | wide

Putting the drivers in the controller is the decision everything else depends on. In cluster mode the driver runs on a worker and dies with the cluster; in client mode it outlives the cluster, and the controller can stop it and start a new one against another master. The controller also sees a failure from two sides, the master's view of the cluster and the driver's view of task progress, so it can tell a dead master with working executors from a dead cluster, the kind of distinction gray failures demand [@huang2017gray].

@sub Components and Interactions

Every two seconds the controller probes each master's JSON endpoint and each running driver's REST API, computes a health score per cluster (C1), and updates a failure-detector state machine per cluster. It then applies the recovery rules to every job (C3) and, when a job must start or move, picks a cluster with the placement cost (C4). Each state change and action is logged with the contribution of every health signal (C5). The data science programs use the rds library, which provides resumable stages and the adaptive checkpoint policy (C2); the controller estimates the mean time between failures from observed outages and passes it to each attempt.

During a cluster outage, probes to A's master time out and its health score falls; after three low scores A is marked failed. The job's driver stops reporting finished tasks, so after a short stall threshold the controller kills it, chooses B, and starts a new attempt with the same job identifier. That attempt finds the commit markers left in object storage, reloads those stages and computes only the rest.

@sub Layered Analytics Stack

Fig. {fig:stack} shows the system as layers, which Sections VI to XII follow. Shared object storage sits at the bottom, with the Spark clusters and the rds library inside each driver above it. The control layer handles monitoring, detection, recovery and orchestration, the explainability layer turns decisions into auditable records and scores, and governance spans all of them. Observability runs through every layer, as is usual for container-based systems [@usman2022survey, @li2021enjoy].

@figure stack | Fig 07 Layered Analytics Stack | Layered analytics stack; observability and governance span all layers, each detailed in Sections VI to XII.

@sub Failure Domains and Assumptions

We separate three failure domains. The design survives the loss of any number of cluster domains (a master with its workers) as long as one remains. The storage domain is assumed available, which in production means a replicated service, and the control domain, the controller with its drivers, would run as replicas. Faults are fail-stop or fail-slow; Byzantine behaviour is out of scope. Stage functions are assumed deterministic, as Spark's lineage recovery already assumes [@zaharia2012rdd].

@sub Deployment Model

The testbed runs everything under Docker Compose on one machine, which keeps experiments repeatable and faults precise. In production, A and B would be separate deployments in different zones or clouds, with a replicated object store and redundant controllers. Multi-cloud orchestration and geo-distributed analytics already handle data placement between such sites [@tomarchio2020cloud, @bergui2021survey], which is why the placement cost in Section X has a data-transfer term, zero in our shared-storage testbed.

@sub Architecture in the Executed Experiments

The experiments used exactly this architecture. Every job started in client mode against master A, every fault hit the job's current cluster, and the same control loop that serves the API carried out every recovery. In outage runs the probes showed A was gone, the driver showed progress had stopped, and the next attempt went to B on the same storage. Across the 36 runs and the case studies no component needed a manual restart.

@section Distributed Data Engineering Layer

@sub Ingestion and Storage Organisation

All durable data lives in an S3-compatible store with three buckets: data for inputs, checkpoints for stage and streaming checkpoints, and results for outputs. Object storage separates data from compute, as data lakes and lakehouses do [@sawadogo2020data, @hai2023data, @harby2024data, @errami2023spatial], and it is what makes cross-cluster recovery possible, since any cluster can read any committed stage. Fig. {fig:pipeline} shows the pipeline our workloads use.

@figure pipeline | Fig 08 Distributed Data Engineering Pipeline | Data engineering pipeline: inputs in the data bucket, resilient stages committing to the checkpoint bucket, outputs in the results bucket. | wide

A seeded generator creates four million synthetic taxi trips, about one per cent deliberately invalid for the cleaning stage, plus a skewed graph with two million edges for the iterative workload, so every team member and reviewer gets identical data. A download script and ingestion job add the NYC taxi records, the AI4I 2020 maintenance data and the ULB credit-card fraud data, and a normalisation function maps the real taxi schema onto the synthetic one.

@sub Transformation with Resilient Stages

Transformations are plain PySpark functions decorated as stages of a ResilientPipeline. In the ETL workload, a cleaning stage drops trips with implausible duration, distance, fare or speed; an enrichment stage joins zones with a borough lookup; an hourly aggregation computes counts, mean and 95th-percentile fares, speeds and tip rates; and a ranking stage uses a window function to pick each borough's top revenue zones. Each stage is a pure function of its inputs, which makes rerunning it and reloading its output equivalent.

If an earlier attempt left a commit marker, the stage's output is read back and the function is skipped. Otherwise the function runs, its result is persisted and forced with a count so the recorded compute time is genuine, and the checkpoint policy decides whether to write it. Data is written first and a small JSON marker second, so a stage counts as committed only when complete, and half-written output from a crashed attempt is never read. Reading the committed data back also cuts the lineage, so a later failure no longer drags earlier stages back into recomputation, and the next attempt simply overwrites any partial output it finds.

@sub Streaming Data Path

Streaming progresses in micro-batches, not stages. Structured Streaming already saves offsets and state after every micro-batch [@armbrust2018structured]; RMC-Spark puts that location in the shared checkpoint bucket, so a query resubmitted on another cluster under the same identifier continues from its last committed batch. For each micro-batch the driver logs one event with the input row count, the processing rate and the batch duration, which the analysis uses to measure how quickly throughput recovers after a fault.

@sub Metadata Management and Schema Evolution

Each marker records the stage name, its position, the job identifier, the attempt number and a timestamp. Together the markers are the resilience layer's metadata catalogue, read at the start of each attempt. In strictly linear pipelines, such as the iterations of an iterative algorithm, the library skips every stage before the latest committed one instead of recomputing results that a later checkpoint already contains. Stage timings go into a per-job event log used to compute recomputed work and checkpoint cost.

Stage outputs are Parquet files that carry their own schema. Because stage identity includes the job identifier, changed pipeline code should use a new identifier, so old checkpoints are never mixed with new code. Schema evolution techniques [@chillon2024generic] and automated governance [@nadal2022operationalizing] could extend this, for example by storing a code version in the marker.

@sub Partitioning and Storage Management

We use 16 shuffle partitions with adaptive query execution, and inputs are generated in 16 partitions for the four executor cores per job. Checkpoint data is kept per job identifier, so storage grows with the number of jobs and can be reclaimed by a retention policy once a job has succeeded. Table {tab:dataeng} summarises the components. Unreliable intermediate data and missing validation are common causes of pipeline failure [@foidl2023data, @taleb2021big]; the commit protocol covers reliability, while validation remains the pipeline's job.

@sub Data Quality in Resilient Pipelines

Resumption rules out reruns that read half-finished files and quietly produce wrong totals, but it can reuse stale results if inputs change between attempts. A reloaded stage reflects the inputs that existed when it was computed. We assume inputs stay fixed during a job, which holds for our batch workloads; changing inputs would need an input version in the identifier or marker, following Section XII.

@sub Data Volumes in the Experiments

The executed matrix used 1.5 million trips in 16 partitions, giving warm fault-free ETL runs of one to two minutes. Committing every stage cost B2 four checkpoints per clean run, raising its median runtime from 92 s to 114 s, while P's adaptive policy wrote none.

@section Spark Processing and Execution Layer

@sub Spark Execution Model

Each cluster runs Spark 3.5.3 standalone: a master tracks workers and allocates resources, and workers start executors. Fig. {fig:execution} shows the setup. Every application begins with a driver, which builds the program's logical plan, optimises it, splits it into jobs and stages, and schedules tasks on the executors [@zaharia2016apache, @armbrust2015spark]. Executors run the tasks, cache partitions, and send status and heartbeats back to the driver.

@figure execution | Fig 09 Spark Execution Architecture | Spark execution in RMC-Spark: the driver runs in the controller in client mode and executors on the selected cluster use shared storage.

The controller starts each driver in client mode with 512 MB of memory; executors get one core and 576 MB, up to four cores per job. The driver advertises the controller's host name so executors on either cluster can reach it, and the controller assigns its UI port to read progress through Spark's REST API.

@sub RDD Lineage and DAG Scheduling

Spark represents a computation as a DAG of RDDs linked by narrow and wide dependencies [@zaharia2012rdd]. A narrow dependency, such as a filter or a map, computes each partition from one parent partition, so such steps are pipelined within a single stage. A wide dependency, such as a group-by or a join that needs a shuffle, reads from many parent partitions and starts a new stage. The DAG scheduler submits stages in topological order and the task scheduler prefers executors that cache the input. Fig. {fig:dag} shows the ETL workload's DAG with the resilient stage boundaries.

@figure dag | Fig 10 DAG Processing Workflow | DAG of the ETL workload: Spark stages inside resilient stages; a committed stage cuts the lineage. | wide

When an executor is lost, the driver reruns the smallest set of tasks that rebuilds its partitions, sometimes reaching back through several shuffles. With many wide dependencies this is the long-lineage problem [@kweun2020lineage]. A committed resilient stage cuts the lineage, because downstream stages read from object storage, and Section IX's policy decides where such cuts pay off.

@sub Task Execution and Built-in Fault Tolerance

Spark's own mechanisms stay on in every configuration. A failed task is retried up to four times; executors send heartbeats every 10 s and are declared lost after the 60 s network timeout; adaptive query execution tunes shuffle partitions. The proposed configuration also enables speculative execution, Spark's standard answer to stragglers [@zaharia2008late]. Spark tuning and performance prediction are active topics [@herodotou2020survey, @cheng2020efficient], but we fixed and documented our settings so that differences come from the resilience mechanisms, not tuning.

@sub Interaction of Built-in and External Recovery

The two recovery layers must not interfere. If Spark is still retrying when the controller considers migration, the rule that a FAILED cluster must have gone ten seconds without any finished task means Spark has had its chance and failed. A long but healthy task could trip the stall signal, so stall alone only makes a cluster SUSPECT, and migration also requires FAILED. The mechanisms are therefore stacked: Spark handles whatever it can inside the cluster, and the controller acts only when the evidence says the cluster as a whole cannot carry on.

@sub Distributed Processing Flow

Every job follows the same flow. The controller places it and launches attempt zero; the driver gets executors and the rds library reloads committed stages, computes the rest and checkpoints as the policy decides. While the driver writes stage events, the controller reads task progress from it. It records a success when the job finishes, or, if the driver crashes or the cluster fails while the job is stalled, starts the next attempt on the same or another cluster according to Section IX.

@sub Measured Execution Profile

In B1's clean runs the median compute time was 23.5 s for cleaning, 10.6 s for enrichment, 14.5 s for aggregation and 6.1 s for ranking, about 55 s in total, against a median completion time of 92 s. The rest went on starting the driver and acquiring executors, 13 s to 35 s per attempt, and writing results. For short jobs this fixed cost is about as large as the work itself, which is why restarting a short job on another cluster costs little more than running it normally.

Over the whole experiment, utilisation was 0.86 for cluster A and 0.04 for B. This reflects the design, since every run started on A so faults could be aimed at a known cluster; in production the placement cost would spread jobs over both clusters, so the second cluster adds throughput instead of idling.

Speculative execution, enabled in the proposed configuration, changed no fault-free result. In the executor-kill runs P finished in a median of 140 s, against 148 s for B2 and 160 s for the single valid B1 run; with one to three runs per configuration this gap is within the testbed's normal variation, and we do not credit it to speculation.
