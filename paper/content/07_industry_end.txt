@sub Banking and Financial Services

Financial institutions run analytics whose value decays within minutes, such as fraud screening, risk aggregation and regulatory reporting. Distributed big data approaches to Internet financial fraud detection show that such workloads are naturally expressed as distributed graph and machine learning pipelines [@zhou2021internet]. Fig. {fig:finance} shows how RMC-Spark would be deployed for a fraud analytics pipeline: transactions land in replicated object storage, feature and model-scoring stages run as resilient stages on a primary cluster, and a second cluster in another availability zone takes over if the first fails. The case-study workload applies the machine learning pipeline of W2 to the ULB credit-card dataset, which contains anonymised card transactions with a highly imbalanced fraud label, and injects a cluster outage during model training. @sub Healthcare

Healthcare analytics combines clinical, operational and device data, and big data analytics in healthcare is used for both treatment and health management [@batko2022use]. Two properties of this domain matter for resilience. First, some analyses support time-critical decisions, for example capacity planning during surges. Second, patient data are subject to strict jurisdictional rules, so failover must not move data to an unauthorised location. The jurisdiction-aware placement described in Section XII addresses the second property by excluding clusters through the transfer-cost term.

@sub Telecommunications

Telecommunication operators analyse network and customer data at very high volume for planning, churn prediction and service assurance, and governance and architecture are central concerns in such deployments [@kastouni2020big]. Streaming analytics on network telemetry is the relevant pattern here, corresponding to workload W4; for such jobs, the streaming checkpoint in shared storage allows continuation on another cluster without data loss.

@sub Manufacturing

Predictive maintenance combines Internet of Things data with machine learning to anticipate equipment failures [@rosati2022from]. Fig. {fig:manufacturing} shows a smart manufacturing analytics platform built on RMC-Spark, in which sensor streams feed both a streaming anomaly job and a periodic model-training job. The second case-study workload trains the W2 pipeline on the AI4I 2020 predictive maintenance dataset, which contains process measurements such as temperatures, rotational speed, torque and tool wear with a machine-failure label. @sub Case Study Protocol

Both case studies follow the same protocol. A reference run without faults trains the model and records its quality metric. A fault run injects a cluster outage on the job's cluster while the training stage is running, so that the job must be migrated and the feature stage restored from its checkpoint. The comparison then checks three properties: whether the job completed, how much work was redone, and whether the model quality of the resumed run equals that of the reference run. Equal quality is expected because both runs use the same seeded data split and the same seeded learning algorithm; a difference would indicate non-determinism in a stage and hence a violation of the resumption assumption of Section IX.

@sub Smart Cities and Cybersecurity

Smart city platforms integrate data from transport, energy and public services, and analytics architectures for smart cities and companies emphasise integration across many sources [@fugini2021big]. Spatio-temporal analytics ecosystems add resource management challenges of their own [@liang2023survey]. Cybersecurity analytics, finally, must scale with attack volume: the scalability of big data cyber security analytics systems has been studied explicitly [@ullah2021scalability], and deep learning intrusion detection has been implemented on Spark [@haggag2020implementing]. For security monitoring, losing the analytics platform during an incident is particularly costly, which makes cross-cluster failover attractive. Table {tab:usecases} summarises the use cases.

@sub Lessons for Adoption

The use cases suggest three lessons for adopting the approach. First, the largest benefit is expected for long, expensive pipelines whose results are needed by a deadline, such as model retraining or end-of-day risk aggregation; short ad hoc queries gain little because restarting them is cheap. Second, domains with data-residency constraints need placement policies before automatic failover is enabled, otherwise recovery could create a compliance incident. Third, teams must adopt the discipline of deterministic, idempotent stages; this is good practice anyway, but it requires care with random seeds, timestamps and external side effects.

@section Challenges and Limitations

@sub Cross-Cluster Synchronisation

RMC-Spark synchronises clusters only through shared object storage and a central controller. This keeps the design simple, but it makes both the object store and the controller critical. In the testbed, the single MinIO instance and the single controller container are single points of failure; a production deployment requires replicated object storage across failure domains and several controller replicas with leader election, so that exactly one replica acts on each job. Fig. {fig:challenges} places these and the following limitations on a roadmap.

@figure challenges | Fig 29 Challenges and Limitations Roadmap | Challenges and limitations roadmap: current limitations of the testbed and design, the risk each one poses, and the mitigation planned in the short, medium and long term.

@sub Execution Semantics

Stage execution is at least once. If a migrated attempt overlaps with a late write of the old attempt, both write the same deterministic output and the commit marker is rewritten, so the result is correct but work is duplicated. Stages with external side effects, such as sending notifications or writing to a database, would need deduplication or idempotency keys. Determinism is also a requirement on the user: stages with unseeded randomness would produce different results after resumption.

@sub Latency Overhead and Network Bottlenecks

Checkpoints cost time and storage bandwidth, and materialising each stage to measure its compute time adds a pass over the data. In geo-distributed deployments, reading committed stages from a remote store adds wide-area latency and cost, which geo-distributed analytics research shows can dominate job time [@bergui2021survey, @mostafaei2022delay]. The transfer term of the placement cost is the hook for handling this, but it is not exercised in the single-host testbed.

@sub Operational Complexity and Cost

Running two clusters and a controller is more complex than running one cluster, and the thresholds of the health model must be understood by the operators who rely on them. The thresholds were set by reasoning about the signals rather than tuned on data, and a sensitivity analysis is still missing. Deployment cost rises with the second cluster, although, as Section XIX notes, the second cluster also adds throughput.

@sub Dependence on Determinism and Data Size

The approach assumes deterministic stages and moderate stage outputs. Stages that call external services, use unseeded randomness or depend on wall-clock time violate the first assumption. Stages whose outputs are very large make checkpoints expensive; the adaptive policy then checkpoints rarely, and recovery approaches lineage recomputation. Very small stages, conversely, add materialisation overhead without much benefit, and a production library would merge them.

@sub Threats to Validity

Internal validity is limited by the shared host: clusters compete for CPU, memory and disk, so a fault on one cluster can affect the other, and absolute timings do not transfer to other machines. External validity is limited by the workloads and data sizes, which are small compared with production analytics, and by emulated rather than real network faults. Construct validity depends on the metric definitions; using recovery criteria from published benchmarks [@vogel2024comprehensive] mitigates this risk. Conclusion validity is limited by three repetitions per cell, which is why comparisons are made over all faults of a configuration with non-parametric tests.

@section Future Research Directions

Fig. {fig:roadmap} outlines a research roadmap. The first direction is predictive recovery. The health model is reactive, but it has a simple interface: any model that outputs an anomaly level per cluster can contribute a signal. Failure predictors trained on cluster traces [@gao2020task, @asmawi2022cloud] and workload forecasting models [@saxena2023performance] could add a predicted-failure signal, allowing the controller to checkpoint or migrate before the failure, as proactive cloud schedulers already do [@alahmad2021proactive].

@figure roadmap | Fig 30 Future Research Roadmap | Future research roadmap: predictive recovery, federated multi-cluster management, Kubernetes and serverless back-ends, and agentic, explainable orchestration.

The second direction is federated cluster management across organisations and clouds. Federated learning shows how models can be trained across sites without moving raw data [@imteaj2021survey], and distributed machine learning systems face similar placement problems [@verbraeken2020survey]. A federated RMC-Spark would place and move jobs across administrative domains under data-residency constraints, extending the jurisdiction-aware placement of Section XII.

The third direction is new execution back-ends. Kubernetes-hosted Spark and serverless analytics change how drivers and executors are started [@schleiersmith2021what, @hassan2021survey], and the controller's submit and stop operations could target them without changing the decision logic. Evaluating a Kubernetes back-end is the most immediate extension of the experimental matrix.

The fourth direction is agentic and self-healing orchestration. Large language models are being explored for AIOps tasks such as incident analysis and remediation [@zhang2025survey], and the joint view of MLOps and AIOps emphasises closing the loop between operations and model development [@diazdearcaya2023joint]. An agent could read the decision log, propose configuration changes, or explain incidents in natural language, while the deterministic controller keeps responsibility for safety-critical actions. Fig. {fig:nextgen} sketches such a next-generation architecture.

@figure nextgen | Fig 31 Next-Generation Resilient Analytics Architecture | Next-generation resilient analytics architecture: predictive signals and an advisory agent added to the deterministic, explainable control loop, with federated clusters and multiple execution back-ends.

Further directions concern the controller itself. Learned checkpoint policies could replace the analytical interval when failures are not memoryless, for instance by conditioning on time of day or on recent anomaly scores, similar to convergence-aware checkpointing for training jobs [@li2024convergence]. Formal verification of the state machine and recovery rules would provide guarantees that testing cannot, for example that no job is ever migrated while making progress. Energy and cost awareness could be added to the placement cost, so that failover prefers clusters with spare capacity or lower price, which multi-cloud scheduling research already considers [@zhu2021task, @tomarchio2020cloud]. Finally, sensitivity analysis of thresholds and weights, and their automatic calibration from incident data, would reduce the dependence on expert judgement noted in Section XI.

@section Conclusion

This paper addressed a gap between the fault tolerance that Apache Spark provides inside a cluster and the availability that analytics consumers expect when a whole cluster fails. It presented RMC-Spark, which combines resumable data science program stages with a cross-cluster resilience controller. The rds library makes PySpark stages idempotent and resumable through a commit-marker protocol on shared object storage and checkpoints them adaptively using the Young and Daly optimum interval with an online MTBF estimate. The controller scores cluster health from five explainable signals, detects failures with a hysteresis state machine, migrates only jobs that stopped making progress, places jobs with an interpretable cost function, and records every decision with its cause. Fig. {fig:contribution} summarises how these contributions relate to the problems identified in Section II.

@figure contribution | Fig 32 Research Contribution Framework | Research contribution framework: problems identified in Section II, the components that address them, and the evidence used to evaluate each one.

The implementation is complete and openly available, its decision logic is verified by automated tests including a simulated cluster outage, and a reproducible evaluation with nine fault types, four workloads and five configurations has been specified together with its statistical analysis. [[Replace this sentence with the two or three main measured findings and whether hypotheses H1 to H5 were supported.]] For practitioners, the main implication is that cross-cluster resilience for analytics does not require changes to the engine: a thin programming library and an explainable controller are sufficient to turn cluster outages from failed jobs into automatic recoveries, at a cost that each organisation can weigh with the model of Section XIX. Future work will add predictive signals, Kubernetes and federated back-ends, and replicated control and storage planes, and will evaluate the approach at production scale.

Several lessons emerged from designing and implementing the system. Placing drivers outside the clusters was the single most important decision, because it made the difference between a job that dies with its cluster and a job that can be moved. Distinguishing degradation from failure, and failure from a stopped job, avoided the main weakness of timeout-based high availability, namely restarting work that would have finished. Making every decision explainable required no sophisticated machinery once the models were chosen to be additive, which suggests that explainability is often a design choice rather than an afterthought. Finally, expressing the experiments as code, with seeded data and scripted faults, made the evaluation reproducible by anyone with a workstation and Docker, which is valuable for teaching as well as for research.
